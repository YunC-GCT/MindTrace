# v7 目标架构评审（2026-10-27）

## 结论摘要

- 总体判断：**有条件可落地**；先钉住端口、运行上下文、事件和发布语义，再迁移业务图。
- `NoteAgent` 可作为笔记域工作流边界，但现有四条分支不是同一种“分类→结构化→校验”流程，不能只改图形而沿用含混结果契约。
- ArkTS 的 `StateGraph` 支持串行异步节点和运行上限，不提供一等子图、跨图预算或通用 Trace；§17.3 的核心工作量是真正补运行语义与验证。
- §17.5 目前主要是端口名称，没有足够的版本、幂等、错误、取消和审批字段；§17.6 把端口放在子图之后，顺序有硬依赖倒置。
- §9、§16 与代码/验收记录存在过期或互相矛盾处；§17 的 AgentRuntime、NoteAgent、ReviewAgent、MathVideoAgent 等均是目标概念，不是现存组件。

## 1. 分层自洽性

**结论：存疑。依据：** §17.1 把 `common` 同时定义为运行内核、MCP/RAG/模型网关和 Data Access，把 `entry` 定义为 App Store 与组合根；§17.5 又将端口放在 common、实现放在 entry（`docs/system-architecture-layered.md:566`、`:568`、`:615`、`:622`）。这种“契约在 common、实现与数据在 entry”的分工可成立，但“App Store 归谁”需要改成明确的接口/实现所有权。实际依赖是 entry→agents/common、agents→common、cardservice→common；`skill/SkillAbility.ets:2` 当前自己初始化 `DatabaseHelper` 并组装 `ToolCatalog`，`entry/src/main/ets/services/NoteEvidenceService.ets:13` 直接拿 RDB 并扩展 `kg_edge`，都还不是 §17 所说的纯入口/端口调用。Manifest 还声明 skill 依赖 agents，但其实现尚未调用 Dispatcher。`scripts/process-boundary/check.mjs:2` 检查进程可达 Kit，不检查一般模块依赖方向。**建议：** 文档写成允许的依赖图而非单链箭头，并在依赖检查中单列模块方向；统一约定 `common` 放稳定领域契约/纯运行机制，entry 持有 RDB、平台适配和组合根，业务写入只能经授权端口。

**Dispatcher 与单一职责，结论：存疑。依据：** 当前 `Dispatcher` 有四种入口语义：prepared candidate、regenerate、generation、capture（`agents/src/main/ets/core/Dispatcher.ets:119`、`:122`、`:125`、`:131`）；它还构造验证/持久化图，并消费 DAO 与 generation repository（`:1443`、`:1539`、`:1646`）。路由与串起阶段本身属于主编排器职责，但由它直接处理候选提交、事务结果和 run 日志会把决策与副作用耦合。当前 UI 的 `confirmDraft` 先编辑/保存 checkpoint，再调用 Dispatcher 提交（`entry/src/main/ets/services/AiService.ets:742`、`:759`）。**建议：** Dispatcher 保留“选 Agent、协调阶段、返回终态”的职责；确认授权与 publish/commit 由明确的 command/port 执行，卡片刷新继续作为提交后可重试副作用。

**§17 与代码不符（单列）：** `AgentRuntime`、`RunContext`、通用 `EventSink`/Reducer/Checkpoint/Trace、三个目标 Agent、`ArtifactStorePort`、`RunStore`、Review/MathVideo 子图和 `common/mcp`、`common/rag` 当前均未找到实现；现有近似物是 `StateGraph`、`ToolLoop`、`CancellationToken`、`NoteGenerationProgressSink`、`NoteGenerationRepository` 与 entry 中的 RAG/DAO。`CardSnapshotStore` 确实在 common，但它是 Preferences 静态读写实现，不是抽象端口（`common/src/main/ets/kit/CardSnapshotStore.ets:20`）。建议将目标项标为“待新增”，并为每个现存近似物注明不可互换的语义。

另有三处 as-built 口径需校正：§3.0 把 LangGraph 说成运行时，ADR-0008 实际采纳的是 LangGraph 工作流模型，执行器是自建 ArkTS（§3.0、ADR-0008 Consequences）；§3.0.1 称 checkpoint/interrupt 可直接用原生能力，与 ADR-0008 明确不引入二者相冲突。§9 称小艺真机未通、观测为零过期：phase tracker 已记录 P0 真机小艺回复和验收日志，同时当前 A2A 仍未调用 Dispatcher（`docs/agents/phase-tracker.md:22`、`:32`）；现有 A2A、capture、模型路由都有日志，但没有统一的跨工作流 Trace（`entry/src/main/ets/agentextability/AgentExtAbility.ets:569`、`entry/src/main/ets/services/AiService.ets:121`）。建议拆开“协议可用”“小艺触发真实整理”“统一追踪”三种验收。

## 2. 子图拆分

**结论：存疑。依据：** NoteAgent 的域边界合理，但 §17.2 的 `classify → structure → verify` 不是四条现有路径的共同语义。普通 capture 有 OCR、可选分类、structure、truth check、persist，`analysisOnly` 在分类后结束（`Dispatcher.ets:132`、`:1678`）；generation 有 light/standard/deep、预算降级、澄清、迭代验证和 checkpoint；regenerate 有章节锁定与 baseVersion；preparedCandidate 已过生成，只做候选 hash/checkpoint 校验、truth check 与提交（`:401`、`:1443`）。分类和验证失败目前有结构化错误、阶段、可重试标记或专属错误码；扁平化成子图通用错误会丢失调用方语义。A2A 收到文本后走 ReplyService，回执意图则直接读 receipt 并返回，二者均不经 Dispatcher（`AgentExtAbility.ets:300`、`:363`、`:503`；phase tracker `:32`）。当前取消也只是 State 上的协作 token：节点前后检查，不能撤销已经提交的 RDB 写入（`agents/src/main/ets/graph/nodes/PersistNode.ets:9`、`:39`、`:77`）。**建议：** 先定义不同 `NoteCommand` 与 discriminated `NoteOutcome`，保留 analysis-only、needs-input、ready-preview、approved/committed、failed、cancelled 等终态；NoteAgent 负责笔记域阶段，主编排层负责审批生命周期和发布。不要把 A2A 协议/35 秒 deadline 放进 NoteAgent；只在确实要让小艺触发整理时，另立端到端变更并先定义 A2A 请求与图片来源。

ReviewAgent 粒度尚存疑：`study_plan` 当前是标题、完成状态、优先级、关联笔记与 due date 的用户待办（`common/src/main/ets/DatabaseHelper.ets:45`；`entry/src/main/ets/database/StudyPlanDao.ets:18`），不是完整复习会话/评分模型。MathVideoAgent 更缺外部 renderer、文件产物、失败重试与取消契约。建议两者暂不纳入 NoteAgent 拆分交付，各自先定产品范围与数据模型。

## 3. 内核可落地性

**结论：存疑；原生递归子图不成立，手工组合可行。依据：** `StateGraph` 是 88 行串行执行器，Node 类型是 `(state) => Promise<state>`；`run` 每次调用重置 `nodeRuns`，默认上限 128，父图没有子图调用 API 或共享运行预算（`common/src/main/ets/workflow/StateGraph.ets:1`、`:19`、`:55`、`:59`、`:67`）。因此可把 `child.run(mappedState)` 包成普通节点，但这只是调用约定，不是具备 parentRunId、跨图事件/取消和累计预算的一等 Subgraph。ToolLoop 已使用同一内核并有 `maxSteps`，可作为稳定机制的参照。

**工作量与风险：** 中高，不是只加一个泛型节点。粗估熟悉 ArkTS 的工程师需要约 1–2 人周完成可生产的 Context/Event/子图预算与取消传播、类型化状态更新和契约测试；不含端口迁移及三类业务图，估算需先用 3–5 天 spike 校准。ArkTS 无 Node/Python；`async` 不会自动换线程，CPU/同步 Kit 卡顿仍会占 JS 线程。spec 034 只证明特定图像 Kit 可在 Worker 使用，不能推导所有 Kit、RDB、UIContext 或对象都可传入 Worker（`docs/specs/034-image-search-isolation.md:5`、§8）。**建议：** 先做可执行 spike：父子图共享 runId/deadline/cancellation，父子累计 node budget，子图失败能保留 domain error；另测 Worker 消息仅传可序列化数据。Reducer 先限定明确的 channel/update 策略，不能用任意对象合并掩盖 copy 漏字段。

## 4. 契约充分性

**结论：不成立（按 §17.5 当前定义）。依据：** 表内只有端口名和归属，没有签名与失败/并发语义。已有业务存储已提供重要先例：`NoteGenerationRepository` 有 run/checkpoint/commit key/cancel/lifecycle log（`common/src/main/ets/models/NoteGenerationModels.ets:324`、`:338`、`:400`），entry `NoteDao` 对写入提供幂等键与版本冲突（`agents/src/main/ets/models/NoteDaoInterface.ets:27`、`entry/src/main/ets/database/NoteDao.ets:66`、`:151`）。但尚无通用 `StudyPlanRead/WritePort`、`ArtifactStorePort` 或 `RunStore`；StudyPlan DAO 是裸 CRUD；CardSnapshotStore 没有 schema version 或读写结果契约。

**建议：** 为每个写命令定义 `operationId/commitKey`、目标版本或 CAS、结构化错误码、幂等重放结果、取消是“未提交/已提交”的可判定语义；NoteWrite 还应要求已批准的 checkpoint/hash 与 expectedVersion，防止 Agent 绕过 HITL。StudyPlan 明确区分用户待办和间隔复习计划。ArtifactStore 需定义 artifactId、媒体类型、URI、校验和、保留/删除与部分失败清理；RunStore 需有 run/parent/event ID、单调 event sequence、status/version、checkpoint 与恢复/取消合同。CardSnapshot 指定 projection schema version、updatedAt、原子替换及刷新失败可重试；Token 事件只记录数量/耗时等元数据，不默认持久化 token 正文。

## 5. 迁移顺序

**结论：不成立（§17.6 当前顺序缺少接口前置与切片验收）。依据：** 步 3–4 先迁 Dispatcher/子图，步 6 才定义数据端口；这会让子图依赖旧 DAO/repository 或暂时绕过接口。步 7 才切换卡片，晚于步 3 的 publish；而当前卡片投影是 NoteDao 原子提交后的 post-commit effect（`entry/src/main/ets/services/KnowledgeUnitPostCommitEffects.ets:25`、`:33`），必须先约定提交与投影失败/重试语义。A2A 则不是 Dispatcher 的前置依赖：当前 `AgentExtAbility` 明确直调 ReplyService，phase tracker 记载其没有 Dispatcher 引用；若 §17.4 把小艺 A2A 纳入 NoteAgent，则这是新增接线，不能由 skill Want 替代（`AgentExtAbility.ets:503`；`docs/agents/phase-tracker.md:32`）。

**建议：** 先完成 ADR，再定义并测试 Note/StudyPlan/Artifact/Card/Run 契约及 entry adapters；随后跑 Dispatcher 四路径的行为基线，再实现最小 kernel 与 NoteAgent 薄包装；先迁单一 capture 路径，稳定后迁 generation/regenerate/preparedCandidate；确认 commit 与卡片投影可重试后切换调用方。A2A 若不纳入则保留其独立契约与 smoke；若纳入，先定义 request/result 映射并在 Dispatcher API 改造前锁定 35 秒 deadline、单帧快照、receipt 短路的验收。旧实现删除与新实现接线必须同一小切片原子完成；不要先合并四条路再一次性删旧实现。最可能出现双写/回滚困难的是步 3 先改写入所有权、步 6 才补端口，以及步 8 跨大切片删除旧实现。

## 6. 与 KnowledgeModel v2 拆分的关系

**结论：成立，但不是同一项拆分，应先后解耦。依据：** ADR 0006 已把原 870 行 KnowledgeModel 拆为结构化与生成协作件，并在 2026-09-09 明确 TruthCheck 由 Capture workflow 的 TruthCheckNode 独占；基线的 `KnowledgeModel.ets` 现在为 102 行 facade，负责组装 CaptureStructurer、DraftComposer、DeepDraftComposer、IncrementalPatchComposer（`agents/src/main/ets/agents/KnowledgeModel.ets:1`、`:35`、`:41`），Dispatcher 另建 TruthCheckNode（`agents/src/main/ets/core/Dispatcher.ets:1657`）。所以 v2 拆分是“类/职责拆分”，NoteAgent 是其上的“工作流组合”，没有必要再拆一次 KnowledgeModel。

**建议：** 先以现有 102 行 facade 和协作类作为稳定组件，补齐四种 dispatch 输入/输出特征测试；NoteAgent 首版只包装现有节点/服务，TruthCheck 仍留在图边界；之后逐条迁移分支。不要同时改 facade API、TruthCheck 所有权和 NoteAgent State，否则会把 ADR 0006 已完成的工作重新打开。

## 7. 可观测性与验证

**结论：存疑。** 现有路径不是“无观测”，但没有统一、持久的跨工作流 Trace。依据：A2A 记录 error code、requestId/taskId、原因、attempts、耗时和单帧快照摘要，35 秒 deadline 取消同一 token 且 `settle` 只回一次（`AgentExtAbility.ets:320`、`:569`、`:595`）；receipt 分支记录命中和计数但不进入 A2A session（`:300`、`:363`）。Capture 有节点耗时（`AiService.ets:121`），NoteGeneration 有 run/checkpoint/lifecycle log。phase tracker 中 P5 导出元数据仍未开始（`docs/agents/phase-tracker.md:29`），因此目前没有可验证的 export artifact 路径。

**建议：** 统一 Trace 至少关联 `runId/parentRunId/requestId/taskId`，记录 node/tool/approval/commit/projection 的开始、终态、耗时和错误码；对 35 秒 deadline 验证取消是否到达 LlmClient、是否只发一次；receipt 事件记录所读 receipt 时间和数据版本；卡片记录源 commit/version 与投影更新时间。导出验收需将 trace runId 与实际文件元数据关联，单有 Trace 不能替代导出物检查。保留正文脱敏约束；当前 A2A smoke + hilog 可闭环协议回复，不应声称已闭环“通过 A2A 整理并入库”。

§1–§9、§14、§16 的 as-built 修正：§5.2 的向量 top-20/embedding/rerank 是目标描述，当前 `KnowledgeUnitChapterEdgeEffect` 明确说 `embedding: []`、相似边待实现（`entry/src/main/ets/services/KnowledgeUnitChapterEdgeEffect.ets:65`）。§16.4 说 `review_item` 已建表，但 `DatabaseHelper.ensureSchema` 的 13 张表含 `study_plan`、不含 `review_item/review_log`（`common/src/main/ets/DatabaseHelper.ets:372`）；§16.1 的 study_plan 又被同时称为复习计划，实际是待办 DAO。§16.2 的 same_unit 当前按同章最近 20 条增量补边，similar 尚未生成（`KnowledgeUnitChapterEdgeEffect.ets:33`、`:65`）。§16.3“渲染不算”基本成立；但 §16.4 的“App 只读”和“App 唯一写入口是用户动作”彼此矛盾（文档 `:294`、`:546`），实际手工编辑与 AI 写入都经 `KnowledgeUnitWriteService`，AI 写入还触发卡片刷新（`entry/src/main/ets/services/KnowledgeUnitWriteService.ets:45`、`KnowledgeUnitPostCommitEffects.ets:33`）。建议以数据 owner + command actor + read projection 三个维度重写这些 as-built 口径，不把表存在、模型有字段或目标设计当成已上线能力。

## 8. 风险清单

1. **嵌套图取消/预算失联。** 早期信号：子图超出 35 秒仍继续请求，或父图 node 上限到达但子图仍运行。缓解：kernel spike 先验证共享 deadline、取消令牌和累计 node/tool budget，并测试取消后底层 HTTP 被销毁。
2. **四种 Note 请求被同一结果类型抹平。** 早期信号：`analysisOnly` 被误持久化、regen 丢 `baseVersion`、preparedCandidate 重复落库，或 needs-input 被当成功。缓解：每条 dispatch 分支先有外部行为基线，使用 discriminated request/outcome 和 commitKey/version。
3. **端口后置导致新旧写入路径并存。** 早期信号：同一 note/run 在 DAO 与新 Port 都被调用，卡片快照落后于已提交版本。缓解：契约和单一 entry adapter 先落地；数据事务是唯一主提交，embedding/edge/card 作为带版本、可重试的 post-commit effects。
4. **common barrel 再次把受限 Kit 带进扩展进程。** 早期信号：process-boundary 出现加载期越界、`:agent` import 求值失败或 A2A 无回复。缓解：新能力先登记进程白名单，改 common barrel 后跑现有 process-boundary gate 与真机 A2A smoke；不把“动态 import 可用”推广成任意 Kit 都安全。
5. **Review/Video 超出已定义的数据和平台边界。** 早期信号：StudyPlan 被同时当待办和复习 session，MathVideo 只能返回脚本却被契约称 mp4，或出现无 owner 的渲染服务调用。缓解：各自 ADR/spec 先确定领域状态、产物存储、隐私、超时/取消、费用和失败重试，再决定是否进入本轮。

## 附：与 §17.7 待拍板项的意见

- **AgentRuntime 归属：** 通用 StateGraph 执行机制留在 common，业务生命周期与错误归 agents；不让 common 依赖 Dispatcher 或平台上下文。
- **AgentFacade：** 若需稳定跨模块入口，可以在 agents 提供类型化 facade；仅当它隐藏多个用例/版本时新增，不做 Dispatcher 的空转发壳。
- **Subgraph 实现方式：** 采用可观察、共享 RunContext 的子图节点组合；不把子图伪装成 Tool，因为 ToolLoop 的重试/输出语义不同。
- **Checkpoint 层级：** 当前保持业务级草稿/审批 checkpoint；通用 runtime checkpoint 暂不做，未来单独 ADR 并先定义序列化兼容。
- **数据归属：** RDB 与平台实现归 entry，接口放 common，业务写操作经审批和幂等 Port；区分 Agent 生成与用户编辑权限。
- **Video：** 暂缓 mp4 renderer；先确认是否只产脚本及产物隐私、存储、Worker/服务、取消和失败恢复责任。
- **ReviewAgent 范围：** 暂不按 `study_plan` 直接展开；先决定它是用户待办还是间隔复习流程，再定义评分、掌握度和复习记录数据。
