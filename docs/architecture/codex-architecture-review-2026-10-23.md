# MindTrace v1 分层架构评审

> **Status**: proposed (2026-10-23)
> **Related**: [分层架构设计](../system-architecture-layered.md)；评审范围按本次需求给定的两周 v1 流程
> **Verified by**: 对照仓库 API 基线、Kit 接入边界与 Agent workflow 决策文档进行静态评审

## 一、必须改的（按严重度）

1. **P0：LangGraph 能力是假设。** 自建 `StateGraph` 没有文档所称的 checkpoint/`interrupt()`。代价：用批次状态机和预览页；退出后重跑，靠幂等去重。
2. **P0：文搜图超出 SDK 基线。** `textSearchImage` 标为 API 26，项目是 API 24；索引范围和设备支持也待证。代价：真机探针后再定，失败则升级 SDK 或移出 v1。
3. **P0：小艺来源白名单不可信。** `Want` 参数中的 caller bundle 不是可信身份。代价：仅依赖系统可验证的身份/权限；否则打开应用并由用户确认。小艺须真机验收，应用内 Want 不算通过。
4. **P1：补齐失败和幂等语义。** RDB 事务不能涵盖文件、Kit 索引、卡片；按图片去重会阻止重做。代价：定义批次/来源 ID、草稿/已写状态；RDB 原子提交，索引和卡片作为可重试副作用。
5. **P1：明确模型与隐私。** DeepSeek 会上传题图/文本，客户端密钥可提取；端侧模型依赖设备服务。代价：告知上传内容，云密钥走服务端；支持设备列入验收，失败不静默切模型。RDB 加密先核 API。
6. **P1：限制端侧资源并核实 OCR 输出。** 20 张并发会挤占内存；置信度、公式、区域坐标未证。代价：逐张释放、限时可取消；无坐标就删区域高亮承诺。

## 二、可以优化的

- **卡片只展示最终快照。** 元服务独立运行，不做确认控制面；刷新失败不回滚笔记。沿用现有 facade/GSKV，接受展示延迟，避免重复业务状态。
- **测试只隔离外部能力。** OCR、模型、RDB、检索留小接口，覆盖失败、重复确认、部分成功；代价是少量适配。

## 三、建议砍掉的

- **砍掉 Plan/ReAct/Memory、多 Workflow、通用 ToolNode。** 唯一流程固定，一个批次服务足够；代价是新场景出现时再抽象。
- **砍掉 Data Augmentation/RAG、向量检索和复习域。** v1 没有问答/复习，Kit 能力也未在项目验证；笔记生成不是 RAG。代价是没有跨笔记检索。
- **MCP 只留最小接口；砍掉工具清单和 A10 跨会话续跑。** 续跑依赖小艺对话关联挂起任务。代价是退出后重发起；应用内取消仍保证不落库。

## 四、你还缺的决策

- 每图可生成几条？重跑去重、覆盖还是新增？
- URI 何时复制、原图/缩略图保留多久、删笔记是否删源图？
- 单图失败能否部分确认？确认写库中断如何恢复？
- DeepSeek 密钥/代理归谁？哪些数据可上传？离线/限流如何处理？端侧模型支持哪些设备？
- 文搜图搜本批还是全库？不支持设备如何降级？
- 唯一验收设备/API、时延目标及小艺入口是否硬门槛？
