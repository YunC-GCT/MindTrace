Architecture

五个模块，三条硬边界

模块数量不是重点；重点是页面不直接碰图执行器，agents 不反向依赖 entry，数据契约留在 common。

模块职责

三个 HAP 负责入口与系统能力，两个 HSP 负责编排、契约与数据。

模块类型职责不做什么
entryHAP页面、浮窗、设置、A2A 扩展能力、ConversationRuntime不直接 import CaptureGraph / CommandExecutor / NoteDao
skillHAP小艺意图与技能入口测试态暂缓，依赖上架
cardserviceHAP服务卡片与学习概览快照不承载业务编排
agentsHSPDispatcher、CaptureGraph、子代理、对话工作流、草稿提交不 import entry，不持有页面状态
commonHSP端口、模型、数据库、LLM 配置、检索与证据契约不依赖 UI

三条硬边界

这些边界由静态检查守住，不靠口头约定。

边界 01

agents 不依赖 entry

工作流可以被 A2A、应用内、后台任务复用；如果 agents 反向 import entry，三个入口就会重新耦合。

边界 02

页面不碰执行器

pages / overlays 只能通过服务层调用，不能直接 import CaptureGraph、CommandExecutor 或 NoteDao。

边界 03

不新增第 6 个模块

新能力优先放进 common 的端口或 agents 的子代理；只有系统入口确实不同才新增 HAP。

本地与云端

笔记不出设备是产品差异点，但“生成”和“向量”需要外部服务，边界必须说清楚。

留在设备

笔记、草稿、计划、判重、检索

RDB / FTS5 / 向量索引、草稿文件、计划文件、inbox、回执都在应用沙箱；判重与证据判定优先在端侧完成。

会出网

用户配置的 LLM 与向量服务

生成笔记、回答、查询改写会调用用户配置的模型；embedding 可走本机 BGE 服务或兼容 OpenAI 接口的端点。

小艺 A2A 只把用户主动发送的消息和生成所需的最小上下文带进扩展；本地笔记不会因为 A2A 而整体上传。
